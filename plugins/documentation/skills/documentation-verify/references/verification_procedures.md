# 文档声明验证流程

## 定位声明和相关实现

逐条记录文档位置、声明及适用条件，区分声明的性质与技术主题。
例如“生产环境超时为 30 秒”属于运行现状，主题是配置；“接口应返回 201”可能是契约要求，也可能是对现状的描述，需结合上下文确定。

从用户提供的信息、README、项目说明、依赖清单、接口调用及源码引用定位相关证据。
从已知入口沿调用、配置或数据流追踪，遇到其他仓库的实现时继续核验可访问的相关部分。
不要求单仓库、多仓库或元仓库等特定组织方式，也不将工作区目录视为全部证据的边界。

- 对已定位的仓库或路径分别搜索，避免混淆同名文件、组件或不同版本。
- 被上层仓库 `.gitignore` 忽略的相关目录仍可包含实现；定向检查已确认的路径，避免搜索工具静默跳过。无需为此遍历所有被忽略内容。
- 缺少仓库、相关版本或访问权限时，记录缺口及受影响的声明；当前目录的无匹配结果不足以证明整个系统没有该能力。
- 核验目标版本与各仓库当前检出版本分开记录；未提交改动属于本地证据，不当作已发布实现。
- 跨仓库证据需说明组件如何连接、版本是否对应。版本组合未确认时，仅报告各自可证实的部分。

## 按声明性质选择证据

| 声明性质 | 主要证据 | 核验重点 |
| --- | --- | --- |
| 当前实现行为 | 对应版本源码、接口定义、校验逻辑、测试或复现结果 | 实际执行路径、条件、默认值和例外 |
| 运行现状 | 部署版本、生效配置、运行状态、日志或观测记录 | 对应环境、时间和实际执行状态；源码只能证明实现能力 |
| 预期要求或契约 | 已确认需求、规范、接口契约及其版本 | 文档是否准确表达要求；实现是否遵守要求另行核验 |
| 历史理由或设计决策 | 对应时期的 ADR、设计记录、评审决策、变更记录 | 决策状态、时间和背景；不能仅从现有代码推导当时动机 |
| 未来计划 | 有效的规划、需求或跟踪记录 | 是提议、已确认计划、已取消还是已完成；不能因尚无实现判错 |

这些证据没有对所有声明都适用的固定优先级。先确认来源回答的是哪个问题，再判断是否支持该声明。
检查来源的适用范围、状态和时效：草稿不能自动代表已确认要求，旧记录不能自动代表现状。
没有实现证据时也不能自行补写“已规划”；计划本身需要依据。
其他文档对同一断言的重复引用不是独立佐证，应追到其原始依据，避免循环印证。

## 实现类声明的核验路径

每条实现类声明至少使用两种不同核验路径；若只能取得一种，记录证据限制，并按其实际证明力给出结论，不能虚构第二条路径。
多次关键词搜索仍属于同一种路径，搜索次数本身不能证明声明成立或不成立。

1. **标识符搜索**：优先使用 `rg` 或 `git grep` 定位名称、键、常量、字段；检查适用的别名或旧名。
2. **入口追踪**：从 CLI、API、配置入口沿调用路径核对实现、分支和调用关系，必要时跨仓库追踪。
3. **测试或复现**：查找覆盖该条件的测试及已有结果；执行时记录版本、环境、命令和结果。测试文件存在不等于测试已运行或线上行为已证实。
4. **定义与校验**：核对 schema、解析器、结构体、校验器和生成来源，区分接口定义与实际执行。

需求、历史和计划类声明使用相应的确认记录核验，不机械要求搜索代码。
运行类声明结合部署与运行证据，不能用两处源码证据替代实际状态。

## 按技术主题检查

### 行为与组件交互

- 定位执行路径，核对开关、模式、依赖、边界条件和错误处理。
- 跨组件或跨仓库声明核对发送、接收、转换和生效环节；缺少任一必要环节时限定结论。
- 局部成功不能证明整个链路成功。

### 配置、默认值与约束

- 核对字段、类型、默认值、允许值、校验与覆盖规则。
- 区分代码默认值、配置模板、发布配置与运行时加载值，按文档描述的层次核验。
- 确认版本或环境差异是否足以解释表面冲突。

### CLI 与 API

- CLI：核对命令、别名、子命令、参数、默认值、帮助信息及输出格式。
- API：核对方法、路径、版本、参数、返回值、错误条件和客户端签名。
- 声明兼容性时检查相关版本与兼容逻辑，不从当前接口存在推导历史版本兼容。
- 契约与实现不一致时分别记录两者；生成的接口文档也需核实生成源、版本和适用状态。

### 示例与预期输出

- 检查语法、字段、依赖、前置条件及其适用版本。
- 输出示例通过对应条件的测试、执行结果或足以推导该结果的实现核对，说明验证方式。
- 为验证而执行示例时，遵守 SKILL.md 的执行边界；未执行的示例不能报告为运行通过。

### 错误信息与术语变更

- 核对错误内容、触发条件、状态码或退出码。
- 核对旧名、新名、兼容别名、弃用或移除的版本证据；搜索未找到旧名不等于已证实其弃用。
- 语言风格另交对应审查，不纳入事实错误。

## 记录证据

共用证据可集中登记并通过编号引用，避免逐项重复。按来源记录足以复核的信息：

- **源码与测试**：仓库标识、提交或版本、文件位置、相关函数，以及影响结论的本地改动；搜索或执行命令用于复核时一并记录。
- **需求、契约、决策与计划**：来源链接或文件位置、版本或日期、确认状态与适用范围。
- **运行证据**：环境、观测时间、部署版本、配置版本和观测入口（在可取得且与声明相关时记录）；注明未知项。
- **缺口**：已检查的来源、找到的事实、尚缺的证据及其对结论的影响。

每项证据只支持其适用范围内的结论；测试、源码和运行状态之间的推断需要有可核实的连接。

## 定性与误报控制

| 分类 | 判定条件与处理 |
| --- | --- |
| 已证实 | 对应性质和适用条件的证据支持声明；注明证实的是实现、运行状态、要求、历史还是计划 |
| 文档不准确 | 有充分且适用的证据证明文档描述错误或缺少必要条件；区分事实描述与要求表达，按各自依据判断是否需要修订 |
| 实现与约定不一致 | 有效且适用的已确认要求或契约与实现相矛盾；分别展示两方，跟进实现偏差或约定变更，不自动改写文档掩盖差异 |
| 证据冲突 | 相关来源相互矛盾，核对版本、环境、时间和状态后仍无法确定哪方适用；列出需要裁定的问题 |
| 证据不足 | 缺少关键来源、权限、版本关联或可核验信息；说明需要补充什么，不作为错误或通过 |

“文档不准确”可进一步说明是错误、过时或不够精确。只有证据表明它曾适用于旧版本、现在已改变时才称为过时。
明确标注的计划、历史或规范不会仅因不同于当前代码就成为缺陷；同一段同时描述要求和现状时拆开核验。
通过源码证明当前实现不支持某行为，需要检查相关入口、分支与依赖边界；充分搜索后的无匹配结果仍不能替代这条证据链。

其他文档可以帮助定位上下文，但“别处有相同描述”不能证实行为已经实现。
发现缺少导航入口等可发现性问题时交给结构审查，不把它当作准确性证据。

## 覆盖范围

核对范围内的声明是否都有结论或明确缺口。
用户要求检查文档覆盖度时，再对照相关实现、契约变更确认 CLI、配置、API 等是否遗漏；不因追踪到更多仓库就扩大到全系统文档审查。
