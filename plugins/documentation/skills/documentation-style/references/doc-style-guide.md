# 通用 Markdown 写作指南

这份指南为项目规范未覆盖的部分提供审查依据。
按 SKILL.md 的规则优先级、语言和文档用途选择适用条款；其中“建议”“优先”等表述是改进方向，不是强制格式要求。
每条发现引用相关规则短句，并说明其与具体文段的关系。

## 基础语言正确性

- 检查普通正文中可确认的错别字、漏字、意外重复词、句子残缺及语法搭配错误；明确指出原文、错误所在与修正方式，不只写“存在语病”。
- 结合完整句子与必要上下文判断。标题、列表项和界面标签可以是短语，强调性重复或刻意引用也有其用途，不按形式机械判错。
- 合法语言变体、项目术语、产品名、代码标识符、程序输出和原文引用不能仅凭词典未收录或不符合常见拼写而判错；不确定时先确认性质。
- 修正建议保持原意；无法确定作者意图时说明歧义或待确认点，不擅自补全条件、动作或技术事实。

## 表达清晰且适合文档用途

- 一段围绕一个主题展开。段落包含多个独立任务或难以跟随的转折时，建议拆分；不按固定句数判错。
- 优先使用读者熟悉的词和具体表述。专业概念在读者首次需要理解时作必要解释，解释深度取决于目标读者。
- 操作步骤明确动作及对象；存在顺序、前置条件或预期结果时清楚表达。解释性文档可以讨论背景、取舍与关系，不要求全部改成操作指令。
- 必做步骤与可选动作在措辞上保持区别，不把“可以”统一改成“必须”。
- 主动表达通常更容易说明谁做什么；被动表达在执行者不重要或强调结果时可以保留，不机械改写所有被动句。
- 建议删除妨碍理解的重复、含混指代和空泛修饰。给出具体替换方案，避免仅评价“表达不好”。
- 语气应适合文档用途；保持要求的强度、条件和例外，不为追求简短而删除影响含义的信息。

## 术语与标识符

- 同一概念优先沿用项目术语表或已明确采用的名称；区分不同概念时保留必要差异，不只因词形相近就统一。
- 产品名称、API、配置键、路径、命令和环境变量按其正式写法保留大小写及字符，不按自然语言规则翻译或改写。
- 缩写在目标读者可能不熟悉时，建议在首次需要处说明含义；不要求每页重复解释通用缩写。
- 正文中作为字面值出现的命令、字段、文件路径等，建议使用行内代码以便与普通词语区分。
- 引用的原文、错误消息、程序输出和代码示例保持应有的准确性；疑似内容错误交给准确性核验，不能当作普通拼写修改。

## 语言与标点

### 中文及中英文混排

- 中文正文优先使用中文标点；代码、命令、URL、版本号和原文引用保留其自身语法所需字符。
- 中英文、数字和单位之间的空格，以及全角或半角的选择，遵循项目约定；没有明确约定时，避免将一种可读写法判为强制违规。
- 英文产品名称与技术标识符保持正式写法。混排文档按各段落语言检查，不将整份文档套入单一语言规范。

### 英文

- 美式或英式拼写按项目或文档明确约定采用；没有约定时，两者都可以接受。非引用正文中的混用可作为一致性建议。
- 标题采用 sentence case 或 title case 按项目约定；未规定时建议选一种并保持一致，保留专有名称的大小写。
- 牛津逗号、引号形式和破折号用法按项目约定，不把某种偏好推广成所有文档的必需规则。
- 标点影响含义或造成歧义时，说明具体歧义再给出建议。

## Markdown 标题与强调

- ATX 标题（`#`）和 Setext 标题（下划线形式）都可以使用；项目未限定时不强制互相转换。
- 标题建议具体说明主题或任务，避免无法帮助定位内容的泛泛标题。操作指南标题可以描述动作，但不要求固定使用“如何”或“How to”前缀。
- 加粗和斜体用于突出对读者有帮助的信息，建议避免整段强调造成重点不清；不为某一产品保留固定强调样式。
- 标题层级、文件命名、分类目录和元数据完整性交给结构审查，不在本指南另设约束。

## 列表、段落与表格

- 有操作顺序的内容用有序列表，并列选项或要点用无序列表；同组列表项的语法与详略程度尽量一致。
- 通用 Markdown 接受多种列表标记；项目未规定时，不因使用 `*`、`+` 或 `-` 的差异判错。编号写法按能否表达和呈现正确顺序判断。
- 缩进和空行应保留预期的段落、列表与代码结构。额外空行数、行宽和语义换行方式按项目约定，不强制固定两行间隔或每个短语换行。
- 表格适合比较、映射和规则清单；长篇解释更适合段落。表格语法以项目实际支持的 Markdown 扩展为准。
- 源文件换行与最终显示不一定相同；判断排版问题时区分源文件偏好与读者实际看到的效果，未知时说明限制。

## 代码、命令与配置示例

- 围栏代码块和缩进代码块都可用于展示代码。项目未限定写法时不强制转换；围栏代码块在语言明确且渲染器支持时，建议标注语言以便阅读。
- 命令与输出应能被读者区分；供直接复制执行的示例建议把命令单独放置，避免将提示符或示例输出一起复制。
- 展示终端会话时可以包含提示符，但应清楚标明输入与输出。不预设某种代码高亮器会自动排除提示符复制。
- 占位符清楚说明需要替换的值，并与真实参数区分。具体符号和大小写按项目约定，代码中的特殊字符保持字面含义。
- 配置示例的格式遵循该语言和项目约定，不对所有项目统一规定 YAML 或 JSON 的缩进宽度。
- 示例文件名、适用环境和必要说明放在读者容易找到的位置；普通文字即可承载，不要求专用 caption 指令。
- 风格修订保持命令参数、代码行为和配置含义不变；运行验证由准确性核验负责。

## 链接文字与图片说明

- 链接文字建议说明目标内容，避免只写“这里”“点击查看”而让读者猜测目标；完整 URL 在需要展示地址本身时可以保留。
- 行内链接与引用式链接均可使用，选择有利于正文阅读和维护的方式；项目未限定时不禁止引用式链接。
- 链接数量应服务于阅读路径，避免同段无意义重复；不强制所有链接只在整页首次出现。
- 图片说明应帮助读者理解图的用途；信息性图片建议有简明替代文字或相邻说明，装饰性图片按其用途处理。
- 链接目标、图片文件与锚点是否有效交给结构审查，风格审查关注可读性。

## 项目扩展与特殊文档

- 提示框、标签页、数学公式、组件及自定义锚点等扩展按项目已采用的语法判断；普通 Markdown 文档无需为了满足本指南引入它们。
- 扩展支持尚未确认时，记录待确认项。已支持的有效扩展不因超出通用 Markdown 就被要求删除。
- front matter 及其字段由项目约定决定，不要求每页必须具备。是否缺失或语法错误由结构审查处理。
- 发布说明、自动生成文档、模板、代码引用或对外原文可有独立约定，先确认适用规则和例外；不套用某个产品的模板或术语。
- `.rst` 等非 Markdown 文件不套用本指南的 Markdown 排版规则；如在审查范围内，可按其实际语言检查表达，专有语法须另有明确依据。
